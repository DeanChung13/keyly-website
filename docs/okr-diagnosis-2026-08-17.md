# OKR 診斷：為什麼第一版只產出量測工作

建立日期：2026-08-17
上位文件：[Keyly 目標拆解（OKR）](okr.md)
起因：開發者回報「目前的 OKR 似乎找不到有效的方向」，具體症狀是「每條路的下一步都是補資料」

---

## 摘要

第一版 OKR（2026-08-15 建立，08-16 修訂）的文件品質高——會撤回錯誤結論、標示證據等級、拒絕無依據推估。**症狀不是紀律不足，恰恰是紀律用錯了地方。**

根因一句話：

> **頂層目標從來沒有被寫成算式，因此無法判斷任何行動「夠不夠」，只能繼續量測。**

本文記錄三項診斷、完整算式，以及三個被撤銷的數字。

---

## 診斷 1：頂層目標沒有算式，所有 KR 因此退化成量測

### 症狀

第一版三條 KR 的主要待辦，全部是量測工作：

| 位置 | 待辦 | 產出 |
|---|---|---|
| 舊 `okr.md:162` | 「排序依零成本策略」 | 讀文件 |
| 舊 `okr.md:163` | 修 `entry_point`、補「開始註冊」事件 | 埋點 |
| 舊 `okr.md:164` | 每月用 skill 複查下載與訂閱 | 報表 |
| 舊 `okr.md:165` | 24 小時後驗證自訂維度有無資料 | 報表 |
| `okr-kr-a-acquisition.md:149` | 下載 Detailed 報告找出搜尋詞 | 報表 |
| `okr-kr-b-activation.md:215` | 註冊 5 個自訂維度、補事件、每月重跑 SQL | 埋點 |

`okr-kr-b-activation.md:9` 的 O 是「**找出**使用者在哪一步停止」——產出是一份文件，不是外部世界的變化。
舊 `okr.md:153` 的 KR-C 是「維持觀察，**不做**定價決策」。

### 機制

頂層目標在第一版是空的：舊 `okr.md:24-25` 的「目標訂閱數」與「達成期限」都寫「待填」。

沒有目標數字，就無法問**「這個行動能把數字推多少？」**，只能問**「我們知道得夠不夠？」**。

而「知道得夠不夠」的答案永遠是「不夠」——樣本永遠可以更大，維度永遠可以更多，基準永遠可以更準。**於是量測成為唯一無法被反駁為「不足以達成目標」的活動。**

這就是為什麼一份紀律嚴謹的文件反而更容易掉進這個陷阱：紀律愈嚴，愈不敢在證據不足時行動；而缺算式時，證據永遠不足。

### 兩處自我抵銷

第一版有兩個地方，文件自己已經寫出了問題，卻沒有據此改變待辦：

**其一**，`okr-kr-a-aso-round-2.md:33` 明寫：

> 達成該目標所需的約 40 倍曝光成長，不可能來自單一關鍵字欄位調整。

文件已宣告該實驗無法達成目標，但整份文件的待辦仍是「2026-09-05 Review Round 1」。**已知不夠，卻仍是主線工作。**

**其二**，`okr-kr-a-competitor-channels.md:165` 把 7 天實驗的失敗定義為：

> 只代表「目前這個帳號 ＋ 這組內容 ＋ 每天 2–3 則回覆」這套做法沒有奏效。

而 `:168-173` 進一步排除了四種推論。結果是：**任何實驗結果都不改變任何決定。** 這在認識論上正確，在決策上等於零價值——一個無論成敗都不改變下一步的實驗，不是實驗。

### 修正

新版 `okr.md` 的四條判定規則直接針對此症狀：

1. KR 必須是一個數字從 X 變到 Y，動詞不得是「找出」「確認」「複查」「評估」「觀察」
2. 埋點、報表、研究不得列為 KR，只能是帶 ≤ 7 天期限的前置
3. 每個 KR 有停損日與停損門檻，到期不補資料、不延期、不改門檻
4. 任何候選行動必須先回答「能推幾倍」，答不出來就不進 KR

## 診斷 2：`3.29%` 被 4 月上線高峰灌水，所有下游推估偏樂觀

### 事實

`okr-kr-a-acquisition.md:42` 的「曝光→首次下載 = 3.29%（225/6,848）」是 2026-04-07 ～ 08-09 的四個月混合值。拆開逐月（同檔 `:40` 與 `:71-79`）：

| 月份 | 曝光 | 首次下載 | 曝光→下載 |
|---|---:|---:|---:|
| 2026-04（自 04-07） | 1,879 | 142 | **7.56%** |
| 2026-05 | 1,157 | 32 | 2.77% |
| 2026-06 | 1,530 | 27 | 1.76% |
| 2026-07 | 1,622 | 19 | 1.17% |
| 2026-08（至 08-09） | 660 | 5 | 0.76% |

2026-04 是上線月（App 於 2026-03-29 前後上架），142 次下載中含直接告知後的下載，不是自然搜尋轉換行為。

**近三個完整月（05/06/07）的實測值是 78 / 4,309 = 1.81%，且逐月下降。**

### 為什麼這是錯誤而非取捨

同一份文件 `:81` 已經指出：

> 全球數字下滑主要來自 4 月上線期的一次性高峰。

**文件知道高峰的存在，卻仍在 `:42` 與 `:93` 用含高峰的混合值做未來推估。** 這是文件內部的不一致，不是保守與樂觀的取捨。

`:93` 的推估因此偏樂觀約 1.8 倍：

> 還差的 75–275 次下載需要約 2,300–8,400 次額外曝光。

以 1.81% 重算應為 4,100–15,200 次。

### 修正

新版 `okr.md` 的基期表改用 05/06/07 三個月。`okr-kr-a-acquisition.md` 已加註更正。

## 診斷 3：三個乘數之中有一個被明確降級，該降級在 1,000 目標下不成立

### 事實

`okr-kr-a-acquisition.md:114` 把產品頁轉換列為「KR-A2（次要）」，理由是：

> 15.7% 與 23.9% 都在一般區間，改善空間存在但不是瓶頸。在曝光量拉起來之前，改截圖的效果會被雜訊淹沒。

### 為什麼不成立

**這個理由在量測上成立，在算式上不成立。**

量測角度：曝光量小時，轉換率的變動確實會被雜訊淹沒，難以歸因。正確。

算式角度：曝光→下載是 `活躍訂閱 = 曝光 × (曝光→下載) × (下載→付費) × (存活率)` 的其中一項乘數。它：

- 完全受開發者控制（截圖、影片、圖示、description）
- 零現金成本
- 不必等 Apple
- 不必等樣本累積

**它是四個乘數中唯一同時滿足這四項的。** 在零成本硬限制下把它降級，等於主動放棄唯一自己說了算的槓桿——只因為改善之後不好歸因。

**歸因是手段，達標是目的。** 當期限只剩 4.47 個月，時間比歸因稀缺。

### 修正

新版 `okr.md` 的 KR-2 撤銷此降級，停損日設為 2026-09-30（四個 KR 中第二早，僅次於不受控的 KR-1）。

## 完整算式

### 定義

```
活躍訂閱 = 曝光 × (曝光→下載) × (下載→付費，毛) × (存活率)
```

四項相乘即為活躍訂閱數。**新版 OKR 的四個 KR 一一對應這四項，不重疊、不重複計算。**

### 基期（2026-05 / 06 / 07，除另註明）

| 乘數 | 現值 | 計算 |
|---|---|---|
| 曝光 | 1,436／月 | (1,157 + 1,530 + 1,622) / 3 |
| 曝光→下載 | 1.81% | 78 / 4,309 |
| 下載→付費（毛） | 1.78% | 4 / 225（全期間） |
| 存活率 | 50% | 2 / 4（全期間，n=4） |
| 下載→付費（活躍） | 0.89% | 1.78% × 50% |

### 目標與期間

- 目標：2026-12-31 前 **1,000 位活躍付費訂閱**
- 現況：**2 位** → 需新增 **998 位**
- 期間：2026-08-17 → 12-31 ＝ **136 天 ＝ 4.47 個月**

### 三種情境

**情境一：轉換維持現況**

```
需要下載   = 998 / 0.0089           = 112,135
需要曝光   = 112,135 / 0.0181       = 6,195,304
每月曝光   = 6,195,304 / 4.47       = 1,386,000
相對現況   = 1,386,000 / 1,436      = 965 倍
```

**情境二：轉換達可達上限**（毛 5.0% × 存活 60% = 活躍 3.0%；曝光→下載 4.0%）

```
需要下載   = 998 / 0.03             = 33,267
需要曝光   = 33,267 / 0.04          = 831,675
每月曝光   = 831,675 / 4.47         = 186,000
相對現況   = 186,000 / 1,436        = 130 倍
```

**情境三：轉換達激進上限**（毛 7.0% × 存活 70% = 活躍 4.9%；曝光→下載 4.0%）

```
需要下載   = 998 / 0.049            = 20,367
需要曝光   = 20,367 / 0.04          = 509,184
每月曝光   = 509,184 / 4.47         = 114,000
相對現況   = 114,000 / 1,436        = 79 倍
```

### 結論

**即使兩段轉換都做到激進上限，曝光仍需 79 倍；以可達上限規劃則需 130 倍。**

毛轉換 7.0% 是 freemium 工具型 App 的頂尖水準；曝光→下載 4.0% 高於 Keyly 上線月（2026-04）以外任何一個月的實測值。這兩個上限已經很難達成，而它們只把需求從 960 倍降到 79 倍——**仍然是兩個數量級。**

### 零成本管道的量級

| 管道 | 已知量級 |
|---|---|
| ASO 關鍵字欄位 | 無證據支持 > 2 倍 |
| SEO | 目標 100 訪客／日；台灣非品牌曝光現為 0 |
| Threads 實驗 | 7 天目標 50 次點擊 ≈ 200／月 ＝ 0.14 倍 |
| 台灣科技媒體 | 單篇導流未知 |
| **Apple Featuring Nomination** | **10–100 倍（不受控）** |
| **產品內分享循環** | **未知，唯一可能自我複利者** |
| **App Store 分類排名** | **未知** |

前四項加總不到 5 倍。**79–130 倍只可能來自後三項。**

而這三項在全部 30 餘份 `docs/` 文件中的評估狀態是：

| 管道 | 出現次數 | 狀態 |
|---|---|---|
| Apple Featuring Nomination | **1 次**（`okr-kr-a-aso-round-2.md:33`，寫「需各自獨立評估」後無下文） | 從未評估 |
| 產品內分享循環 | **2 次**（`okr-kr-a-competitor-channels.md:79,199`，皆為「競品是否有」） | 從未評估 Keyly 自身 |
| App Store 分類排名 | **0 次** | 從未提及 |

**這是本次診斷找到的唯一「新方向」**：唯一有正確量級的三條路，恰好是唯一三條從未被寫過的路。

## 一項待記錄的因果順序

`docs/seo/2026-08-11-next-task-prioritization.md:7` 的零成本硬限制：

> 目前所有主動任務必須零額外現金支出⋯付費廣告、付費 SEO 工具、買連結、付費媒體或合作不列入執行佇列。

**此限制訂於 2026-08-11，早於 08-15/16 才產出的漏斗數據。** 它是依當時假設而非依算式所做的決定。

開發者已於 2026-08-17 看過完整算式後確認**維持此限制**，新版 OKR 據此設計。此處僅記錄因果順序，不構成翻案理由。

### 該限制的可量化代價

以淨收 NT$121／月、假設平均訂閱 6 個月（**未驗證，churn 目前 n=1 無法估算**）計：

```
LTV          = 121 × 6              = NT$726
可容忍 CPI   = 726 × 0.89%          = NT$6.5
```

低於任何實際 CPI。

**因此即使日後解除限制想投放，也必須先修好轉換率才買得起流量。** 這反向支持 KR-3 的優先級：轉換不只影響算式，也是任何付費管道的先決條件。

## 未驗證與限制

| 項目 | 狀態 |
|---|---|
| 毛轉換 7.0%、存活率 70%「是頂尖水準」 | 依一般經驗判斷，**無同類 App 實測基準** |
| 曝光→下載 4.0% 為可達上限 | 依 Keyly 自身歷史推估（2026-04 曾達 7.56%，但含上線高峰） |
| 平均訂閱 6 個月 | **未驗證**。churn n=1，樣本不足 |
| 存活率 50% | n=4。任何百分比在此樣本下都不具統計意義 |
| Apple Featuring 的 10–100 倍 | **無 Keyly 實測，亦無同類 App 案例佐證**。屬機制推論 |
| 產品內分享循環、App Store 分類排名的量級 | **完全未知**，需另立文件評估 |
| 各零成本管道量級的加總「不到 5 倍」 | 依各文件自述目標值加總，非實測 |
